# 高并发秒杀 Demo

同一个场景, 对比 5 种下单写法: 商品库存 100, 同一时刻 500 个请求打过来, 250 个用户每人连点两次.

## 运行

```bash
docker compose up -d        # MySQL 8 + Redis 7, 数据存在 volume 里, 容器删了数据也还在
npm install
npm run dev                 # 终端 1: 启动服务 (同进程里跑 Redis 队列的落库 worker, 页面也由它提供)
npm run bench               # 终端 2: 5 种策略各压测一轮, 打印对比表
```

- 可视化页面: 浏览器打开 http://localhost:3000 . 页面的"同时抢购"在服务端并发执行, 因为浏览器同一域名只开约 6 个连接, 发不出真正的 500 个并发; bench 则是真实的 500 个 HTTP 请求
- 首次启动 MySQL 需要十几秒初始化, bench 报连接错误就稍等再试
- 改了 `sql/init.sql` 后, 需要 `docker compose down -v` 删除数据卷再 `up -d`
- bench 每轮会调用 `/reset` 重置库存和订单, 可以反复跑

## 怎么看结果

| 列 | 含义 |
| --- | --- |
| 成功 | 接口返回 OK 的请求数 (redis 策略里 OK 表示"抢到名额", 订单由 worker 异步写入) |
| 售罄 / 重复 | 被库存或唯一索引拦下的请求数 |
| 失败 | 乐观锁重试用完 (BUSY), 或服务端报错 (ERROR) |
| 订单 / 剩余库存 | 直接从 MySQL 读取 |

正确的写法应满足: 订单数 = 初始库存 - 剩余库存, 且剩余库存不为负.

## 5 种策略

| 策略 | 怎么防超卖 | 代价 |
| --- | --- | --- |
| naive | 不防, 先查后改 | 超卖, 库存变负数; 重复请求扣了库存却没有订单 |
| pessimistic | `SELECT ... FOR UPDATE` 行锁 | 正确, 但请求排队串行执行, 吞吐受限 |
| optimistic | `version` 条件更新, 冲突就重试 | 正确, 但竞争激烈时大量请求重试耗尽 (BUSY) |
| atomic | `UPDATE ... WHERE stock > 0` 一条语句 | 正确且简单, 生产里最常用 |
| redis | Lua 原子预扣减 + 队列异步落库 | 正确, 但架构更复杂, 要处理 Redis 与 MySQL 的不一致 |

## 高并发与数据库安全

**高并发的核心问题**: 大量请求同时读写同一行数据. naive 的"查 → 判断 → 改"之间有空隙, 多个请求都读到 `stock = 100` 并全部通过判断, 然后各自扣减, 这就是竞态条件 (race condition).

**数据库安全 (并发下的数据正确性)**:
- **事务**: 扣库存和插订单放在同一个事务里, 要么都成功要么都回滚. 重复请求在插订单时报唯一索引冲突, 事务回滚, 它扣掉的库存也退回来. naive 没有事务, 库存就永久少了
- **行锁 + 条件更新**: `WHERE stock > 0` 把"判断"和"扣减"合成一条语句, 由 InnoDB 行锁保证原子性
- **唯一索引**: `uk_user_product` 在数据库层拦住重复下单, 即使应用层判断漏了也不会多出订单
- **参数化查询**: 所有 SQL 都用 `?` 占位, 用户输入不会拼进 SQL 字符串, 防止 SQL 注入
- **CHECK 约束**: 生产中可以加 `CHECK (stock >= 0)` 作为最后一道防线. demo 故意不加, 才能看到超卖
- **Redis 与 MySQL 的一致性**: Redis 只负责发名额, MySQL 才是最终依据. worker 落库失败会把预扣的库存退回; `/reset` 自增代号并和落库互斥, 重置前抢到的队列项会被丢弃, 不会在重置后多写一单

**demo 没覆盖的部分** (生产需要补充): 接口限流, 缓存穿透/击穿/雪崩防护, 消息队列的不丢消息与幂等消费.
